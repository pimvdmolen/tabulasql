# Building release binaries

NativePHP builds the desktop app with Electron. All commands run from the
project root with dependencies installed (`composer install && npm install`)
and assets built (`npm run build`).

## Per platform

```bash
# Linux (AppImage + deb, x64)
php artisan native:build linux x64

# Windows (NSIS installer, x64)
php artisan native:build win x64

# macOS (dmg; build on a Mac, pick your arch)
php artisan native:build mac arm64
php artisan native:build mac x64
```

Artifacts land in `nativephp/electron/dist/` (configured as
`directories.output` in `vendor/nativephp/desktop/resources/electron/electron-builder.mjs`).
Electron can only build for the OS it runs on (cross-building Windows from
Linux works with Wine, macOS requires a Mac).

Before building:

1. Bump `version` in `config/nativephp.php` (or set `NATIVEPHP_APP_VERSION`).
2. Set a real `app_id` (`NATIVEPHP_APP_ID`) — reverse-DNS, stable across
   releases.
3. Make sure `.env` does not contain development secrets: NativePHP bundles
   the environment file according to the `cleanup_env_keys` /
   `cleanup_exclude_files` settings in `config/nativephp.php`.
4. `php artisan native:reset` clears previous build output when a build
   behaves strangely.

## Troubleshooting `composer native:dev` on Linux

Two issues show up specifically on Linux dev boxes (VMs, headless servers,
some sandboxed/containerized setups), not on a normal desktop:

**"Command failed: 'npm run dev' (exit code 1)" with no visible reason.**
Run `php artisan native:run --no-interaction -v` (note the `-v`) to see the
real error NativePHP otherwise swallows. Two known causes:

1. *Electron's binary never downloaded.* `npm install` in
   `vendor/nativephp/desktop/resources/electron` can report success even
   when Electron's own postinstall download failed (e.g. no network access
   during that install). Fix: `cd vendor/nativephp/desktop/resources/electron
   && node node_modules/electron/install.js`.
2. *`chrome-sandbox` isn't setuid-root.* Electron's sandboxed renderer
   requires `chrome-sandbox` to be owned by root with the setuid bit. Fix:
   `sudo chown root:root vendor/nativephp/desktop/resources/electron/node_modules/electron/dist/chrome-sandbox`
   then `sudo chmod 4755` on that same path.

**Crashes a few seconds in with `FATAL: GPU process isn't usable. Goodbye.`**
Some environments can't spawn Chromium's separate GPU process at all (even
with `chrome-sandbox` fixed). We patch
`vendor/nativephp/desktop/resources/electron/src/main/index.js` to disable
hardware acceleration and force `--in-process-gpu` before
`NativePHP.bootstrap()` to work around it; TabulaSQL is a plain CRUD UI, so
software rendering costs nothing noticeable.

**External links (e.g. the "buy me a coffee" link) open in a new Electron
window instead of the system browser.** Same file. NativePHP doesn't
register a `setWindowOpenHandler` anywhere, so Electron's default behavior
for `target="_blank"`/`window.open()` is to open a brand new BrowserWindow
with its own title/menu bar. We patch that file to send external
navigations to `shell.openExternal()` instead.

**How these two patches are kept in place:** that vendor file isn't
committed to git and gets fully regenerated by `native:install` on every
`composer install`/`composer update` (nativephp/desktop redownloads its
Electron scaffold), which would otherwise silently drop both fixes. The
maintained, correct version of the file lives in
`resources/nativephp-patches/electron-main-index.js` (tracked in git), and
`composer.json`'s `post-install-cmd`/`post-update-cmd` hooks run
`php artisan native:patch-electron` right after `native:install` to copy it
back into place automatically — nothing manual needed on a normal
`composer install`. If you ever need to reapply it by hand (e.g. after
running `native:install` directly, outside of Composer's lifecycle), just
run:
```bash
php artisan native:patch-electron
```
To change either fix going forward, edit
`resources/nativephp-patches/electron-main-index.js` (not the vendor copy —
that gets overwritten).

## CI notes

`.github/workflows/build.yml` already implements all of this: a matrix over
`ubuntu-latest`, `windows-latest`, `macos-latest` (arm64) and `macos-latest`
(x64), running on push to `main`, on pull requests, and attaching installers
to a GitHub Release when one is published.

- **The bundled PHP runtime needs replacing — this is not optional.**
  `nativephp/php-bin` (the package NativePHP normally downloads its bundled
  PHP from for the shipped app) is built **without `pdo_mysql` or `sodium`**
  — confirmed by extracting it and checking `php-extensions.txt` directly.
  Since this app connects to MySQL/MariaDB and encrypts connection exports
  with sodium, a build using the default bundled PHP would install fine and
  then fail with "could not find driver" the moment anyone tries to connect,
  and would break `.dbmconn` export/import. `scripts/ci/fetch-static-php.php`
  downloads a static-php-cli build that has both instead (from
  `dl.static-php.dev`'s prebuilt "bulk" set for Linux/macOS, "spc-max" for
  Windows), **verifies the required extensions by actually executing the
  downloaded binary** (it always runs on the matching OS, so this is never a
  cross-platform guess), and wires it in via `NATIVEPHP_PHP_BINARY_PATH`. It
  exits with a clear error rather than silently shipping a broken binary if
  anything's missing. See `nativephp-php-bin-custom/README.md` for the
  equivalent manual local-dev setup this mirrors.
- The app's SQLite database is created at runtime in the user's app-data
  directory; no extra build steps needed.
- Code signing: provide the usual Electron env vars (`CSC_LINK`,
  `CSC_KEY_PASSWORD`, notarization credentials on macOS). Unsigned builds work
  for local testing but trip OS gatekeepers — the workflow doesn't attempt
  this yet (no certificates configured).
- SSH tunneling expects `ssh` on the user's PATH at runtime (built-in OpenSSH
  on Windows 10+); password-auth tunnels additionally need `sshpass` on
  Linux/macOS.
- Release asset filenames are intentionally version-free (e.g.
  `TabulaSQL-linux-x64.AppImage`) so a website's download links via
  `github.com/OWNER/REPO/releases/latest/download/<name>` never need
  updating between releases. Tag releases as `vX.Y.Z` — the workflow derives
  `NATIVEPHP_APP_VERSION` from that tag automatically.
